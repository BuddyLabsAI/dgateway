This guide starts dgateway, sends a first decision to its built-in mock and then connects real models. The mock needs no API key.

## Run the image

Start the container. Before you use it beyond a local trial, replace the `ADMIN_TOKEN` and `GATEWAY_SECRET` values with two different long random strings. Keep `GATEWAY_SECRET` the same over time: it encrypts the provider keys you store.

```sh
docker run -d --name dgateway \
  -p 127.0.0.1:8790:8790 \
  -v dgateway-data:/data \
  --add-host host.docker.internal:host-gateway \
  -e ADMIN_TOKEN=replace-with-a-long-random-token \
  -e GATEWAY_SECRET=replace-with-a-separate-stable-secret \
  ghcr.io/buddylabsai/dgateway:latest
```

Inside a container, `localhost` is the container itself. The `--add-host` line lets a container on Linux reach your machine as `host.docker.internal`, for example to call a model server there; Docker Desktop has this name already.

To connect real models, open the console at [http://127.0.0.1:8790/](http://127.0.0.1:8790/) and sign in with the admin token. On **Providers**, add or configure a provider, run **Test** with your chosen model, and turn the provider on. On **Models**, create a route with a step for that provider and model. Send the route name in your request's `model` field. Calls to `/v1/decisions` need no key until you turn on client keys in settings. [Provider setup and compatibility](/docs/guides/providers)

Your app names a route in the `model` field, and the route decides which models answer. A new install has a test route named `default`. It answers with a built-in mock instead of a real model, so you need no API key.

The mock does not read the text. It takes its numbers from a hash of the input, so it shows the response format, not model quality.

Ask it three questions about a support ticket in one request:

```sh
curl http://127.0.0.1:8790/v1/decisions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "default",
    "input": "I got charged twice for my March invoice. Please refund the extra charge.",
    "questions": [
      {
        "name": "team",
        "type": "choice",
        "instructions": "Which team should handle this ticket?",
        "choices": [
          {"value": "billing", "description": "Invoices, charges and refunds"},
          {"value": "technical", "description": "Bugs, errors and outages"},
          {"value": "account", "description": "Login, profile and access"}
        ]
      },
      {
        "name": "refund",
        "type": "predicate",
        "instructions": "Does the customer ask for a refund?"
      },
      {
        "name": "urgency",
        "type": "score",
        "instructions": "How urgent is this ticket?",
        "levels": [
          {"label": "low", "description": "Can wait a few days"},
          {"label": "normal", "description": "Answer today"},
          {"label": "high", "description": "Answer within the hour"}
        ]
      }
    ]
  }'
```

How to read it:

- `choice` is the most likely team. `probabilities` gives the probability of each team.
- The yes/no question returns `probability`, the chance that the answer is yes.
- `score` is the expected level: 0 is low and 2 is high. It is the sum of each level number times its probability.
- `gateway` names the provider and model that answered, lists each attempt and gives the cost in US dollars.

## Run with Docker Compose

From a checkout of this repository, copy the example settings:

```sh
cp .env.example .env
```

Set `ADMIN_TOKEN` and `GATEWAY_SECRET` in `.env`, as in [Run the image](#run-the-image). You can also set provider API keys there; see [providers](/docs/guides/providers). Then start it:

```sh
docker compose up -d
```

Compose uses the published image, binds port 8790 to localhost and keeps data in the `dgateway_gateway-data` volume. `docker compose up -d --build` builds the image locally. `docker compose down -v` deletes the volume. `GET /healthz` needs no token.

## Run from source

Install Bun 1.3. From the repository root:

```sh
bun install
ADMIN_TOKEN=replace-with-a-long-random-token GATEWAY_SECRET=replace-with-a-separate-stable-secret bun run start
```

The API runs right away on `0.0.0.0:8790`. Set `DGATEWAY_HOST` or `DGATEWAY_PORT` to change it. Data goes to `./data`; set `DATA_DIR` to change it.

The Docker image includes the admin console. From source, build it once:

```sh
cd src/modules/gateway/apps/console-web
bun install
bun run build
```

Until you build it, `http://127.0.0.1:8790/` shows a placeholder page. The API works either way. The server looks for the built console in the console's `dist` directory; set `CONSOLE_DIR` to use another one.

## Connect your own providers

Open the console, add and test a provider, then create a route with a step for each provider you want it to try. Try these next:

- [Routes and fallback](/docs/guides/routing): your app keeps one route name while you change the providers behind it. A route can also stay on your own machine.
- [Cost](/docs/guides/cost): what each decision cost and where the number came from: billed, token-priced, estimated or unpriced. dgateway shows spending; it does not stop spending at a budget.
- [Providers](/docs/guides/providers): hosted vendors and model servers on your own machine.
- [Security](/docs/guides/security): stored provider keys are encrypted, and payload capture is off by default.
- [Decision API](/docs/reference/decisions): every field, with tested examples.
- [Synthetic decisions](/docs/guides/synthetic-decisions): how chat models answer decision questions.

`confidence` is not proof that an answer is right. Test your provider, model, instructions and thresholds on examples you have labelled yourself before you rely on them.

A new install has three routes: `default`, `luna` and `elephant`. It also has the `llamacpp`, `typesafe`, `openai-chat` and `openrouter-chat` providers, turned off. `openai-chat` and `openrouter-chat` call chat models to answer decision questions.

dgateway has no chat-completions endpoint and does not choose the best model for a task. See all [limits](/docs#limits).
